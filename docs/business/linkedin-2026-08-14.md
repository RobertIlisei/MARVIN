# LinkedIn drafts — 2026-08-14

Two angles from the same fortnight of MARVIN work. **Draft A** is the stronger
post: it has a reversal, a concrete mechanism, and a lesson that isn't a
platitude. **Draft B** is the design-principle angle — better if the audience is
people building AI tooling rather than people who write software generally.

Nothing here is published. Both are drafts for review.

---

## Draft A — "Four fixes. Same crash." *(recommended)*

Four fixes. Same crash. Then I stopped fixing it.

MARVIN — the pair-programming assistant I'm building — kept dying with an
identical stack trace. Four times I found a real bug, shipped a real fix, and
watched it come back.

The fourth crash was *caused* by the third fix.

That's the tell. When a fix creates the next bug, the abstraction is wrong, not
the parameters. So I stopped patching and did the boring thing: made the app
record what it was actually complaining about.

macOS crash reports carry a backtrace but not the exception's *reason* — the one
field that says what went wrong. I'd been inferring the cause from the stack for
two fixes running. Both were plausible. Both were wrong.

The instrumentation caught it on the first crash after install: AppKit's own
loop-breaker for a layout pass that never converges, thrown from inside the UI
framework rather than from my code. Ten minutes of reading, after two weeks of
guessing.

But here's the part I nearly missed. The instrumentation itself silently failed
the first time.

I hooked it the obvious way — a subclass named in the app's Info.plist. It
compiled. It installed. It did nothing, because SwiftUI creates its own
application object before that key is ever read. No warning. No error. Just
silence that looks exactly like "no crashes yet."

I only caught it because I'd made the hook log one line at startup saying
whether it was armed. Without that line I'd have shipped a diagnostic build,
waited for the next crash, and captured nothing.

Two things I'm keeping:

**Two guesses cost more than one measurement.** I knew that. I did it anyway,
twice, because each guess was plausible and cheap and *felt* like progress.

**A diagnostic that can fail silently has to assert it's working.** "No output"
and "not installed" are indistinguishable from the outside — so make it say
which one it is.

MARVIN is open source (MIT). The full write-up is in the repo as an
architecture decision record, including the two fixes that didn't work and why
I believed them.

## Draft B — "Let it be wrong. Don't let it act."

I gave my AI assistant a job this week that it's genuinely good at, and then
took away its ability to do anything about the results.

The task: my project backlog had grown to 430 items. Duplicates that exact-title
matching can't see. Items whose work quietly shipped months ago. References to
files that no longer exist. A backlog that only grows stops being read — and an
unread backlog is the same as no backlog.

So MARVIN now reviews it. Finds the duplicates, the stale entries, the dead file
references, the items nobody ever triaged.

And it cannot fix any of them.

Not "shouldn't" — cannot. There is no write path in that code. The route is
read-only. The report it produces carries the instruction *"these are
heuristics, do not act on them"* alongside the data, not just in the system
prompt, so it survives being quoted out of context.

That looks like timidity. It isn't. Every judgement in there is probabilistic:
"untouched for 30 days" is not "abandoned." "These two look alike" is not "these
are the same." "That file is gone" is not "that work is done" — the file may
have moved, or the item may be the request to create it.

Acting on a wrong heuristic deletes work nobody agreed to drop. Which is the
precise failure the backlog exists to prevent. An assistant that quietly closes
the wrong item is worse than no assistant, because now you also don't know what
you lost.

The boundary I'd argue for, generally: **where the judgement is probabilistic,
put the line between analysis and application.** Let it be freely wrong in what
it notices. Make it structurally unable to act on being wrong.

Same week, same codebase: I asked it whether to categorise those 430 items, and
it measured them before answering. The data killed my proposed taxonomy — the
categories that actually mattered weren't bug/feature/chore, they were
"investigate" (the output is a decision, not a diff) and "blocked" (waiting on a
human outside the repo, and therefore not pickable at all).

Surfacing beats deciding. Measuring beats both.

MARVIN is open source (MIT).
